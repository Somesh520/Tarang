The pipeline

One search. Three hops. Sound.

Nothing about playback is guessed. Tarang resolves the actual media manifest, picks the best audio the source exposes, and serves it from the nearest edge.

01

Fetch

Search hits our resolver, which queries the catalogue API directly — no page scraping, no embedded player. Results are normalised into our own track model and cached for 24 hours.

02

Resolve

We read the available formats and walk a quality ladder: Opus 160 first, then AAC 128 for Safari. Signed media URLs never reach your browser — they expire and are network-bound.

03

Stream

The first play packages the track into 6-second HLS segments on our storage. Every play after that is a static file fetch from the CDN — so seek is instant and playback never queues behind anyone else.

client → /api/search → resolver → /api/stream/:id → edge cache → <audio>

Straight answers

Questions, answered.

We stream the highest bitrate the source exposes — Opus at ~160 kbps variable, which is transparent for the vast majority of headphones and speakers. Where a higher-bitrate AAC stream exists, we prefer it. We do not pretend this is lossless, and we don't upsample to fake a number.

The launch build resolves tracks from YouTube's public catalogue through its media API, the same class of pipeline used by open-source clients like Flow. That means a catalogue as wide as YouTube itself — and it means playback depends on a third party. We're building the source layer as a pluggable provider so a licensed catalogue can be added without changing the player or your library.

Because we package the track into streamable segments once, at full quality, instead of proxying bytes for every listener forever. First play: resolve + package. Every play after that: instant, from the edge. Popular tracks are pre-warmed before launch.
